# Architecture

Loco separates its control plane from the regional components that run applications. The CLI and dashboard call the API, and the regional agent connects the cluster to the control plane.

## Control plane

The Go API exposes ConnectRPC services and stores platform state in PostgreSQL. The CLI uses Cobra and Charm libraries; the dashboard lives in `web/`. Protocol definitions live in `proto/`, with generated clients in `gen/`. Each region has one control plane: the API, dashboard, observability proxy and ClickHouse, in its own cluster or with an external ClickHouse. Worker clusters attach to one control plane and can run anywhere.

## Regional runtime

The in-cluster agent exchanges state with the API. The controller reconciles Application custom resources into Kubernetes workloads and routing resources. A CNI that enforces NetworkPolicy isolates workspaces; Envoy Gateway handles ingress and TLS termination; cert-manager provisions certificates.

## Registry access

With `LOCO_REGISTRY_AUTH=token` the API is the registry's token endpoint at `/registry/token`. It accepts the Docker token flow, `GET` with HTTP Basic credentials, and the OAuth2 form `POST` with `grant_type=password` that containerd and BuildKit send; `service` must equal `LOCO_REGISTRY_TOKEN_SERVICE`. Each enrolled agent calls `RegistryService.IssuePullCredential` with its cluster assertion and a workspace ID, and receives a random credential with the username `loco-pull`, valid for `LOCO_REGISTRY_PULL_CREDENTIAL_LIFETIME` (24 hours by default). The API stores only its SHA-256 hash, and refuses the call with `PERMISSION_DENIED` unless the workspace has an open placement window on that cluster, or with `FAILED_PRECONDITION` in `static` mode. At the token endpoint, a `loco-pull` credential gets `pull`, and nothing else, on each requested repository under `<LOCO_REGISTRY_PREFIX>/ws-<workspace id>/`, while it is unexpired, its cluster is enrolled and the workspace is still placed there. Each time the API sends a build to a cluster's agent in `StartBuild`, including a resend after the agent reconnects, it creates a new random `loco-build` credential for that build, stores its SHA-256 hash and sends the credential in `registry_credential`. A `loco-build` credential gets `pull` and `push` on its build's repository only, while the build is queued or running on the credential's cluster; every credential sent for the build works until then. If the API cannot store the credential, it does not send the build and tries again on the next dispatch. Enrolling a cluster with a join token, and removing it, deletes every credential issued to the cluster, so neither the previous agent key nor a restore brings them back. The endpoint drops every other requested scope, including other resource types and the empty repository name, and answers an unknown, expired or revoked credential, or a username that does not match its kind, with HTTP 401. A granted request returns an Ed25519 JWT signed with the pinned version of `LOCO_REGISTRY_TRANSIT_KEY`, with `sub` set to the cluster ID, `aud` set to `LOCO_REGISTRY_TOKEN_SERVICE`, an `access` list and an expiry `LOCO_REGISTRY_ACCESS_TOKEN_LIFETIME` (5 minutes by default) after `iat`; the registry verifies it with the key at `/.well-known/loco-registry-key.pem`. A token already issued stays valid until it expires after its credential is revoked. Every `LOCO_REGISTRY_CREDENTIAL_SWEEP_INTERVAL` (10 minutes by default) one API replica deletes expired pull credentials and build credentials whose build is no longer running on their cluster.

In token mode the image sweeper, which deletes old build images, needs no `LOCO_REGISTRY_USERNAME` or `LOCO_REGISTRY_PASSWORD`. For each registry request it signs a token with the same key and lifetime, `sub` set to `api`, without calling `/registry/token`, and the token grants only what that request needs: `pull` on the empty repository name to list the catalog, `pull` on one repository to list its tags or read a manifest, and `delete` on one repository to delete a manifest. A repository with no tags, such as one a refused cross-repository mount leaves behind, has nothing to delete and does not stop the sweep. The registry's token realm must name the API by a DNS name: go-containerregistry, the sweeper's registry client, refuses a realm whose host is a private, loopback or link-local IP literal unless it equals the registry's host and port, even though the sweeper never calls the realm.

On a worker cluster the `loco-worker` chart value `registry.auth` (`static` by default, or `token`) sets `LOCO_REGISTRY_AUTH` for the agent and both controllers. In `token` mode the agent writes each workspace's credential to the Secret `loco-registry-pull-<workspace id>` in its own namespace, of type `kubernetes.io/dockerconfigjson`, keyed by the registry host that `IssuePullCredential` returns in `registry_host` and labelled `loco.io/registry-pull`. It issues the credential before it applies the first Application of that workspace, and a failed issue fails that apply. A Secret with that name but without the label is overwritten. Every `agent.registryCredentialCheckInterval` (5 minutes by default), or sooner when a credential reaches half its lifetime first, the agent renews each credential past half its lifetime, issues one for each workspace with an Application in the agent's namespace and no Secret, and deletes each Secret issued more than one interval ago whose workspace has no Application left in the agent's namespace, counting an Application that is being deleted as gone. A workspace the API refuses with `PERMISSION_DENIED` is logged as an error and the other workspaces carry on. While the API answers `FAILED_PRECONDITION` the agent logs an error and checks again at its longest reconnect delay. On every `StartBuild`, including a resend for a Build that already exists, the agent writes `registry_credential` as user `loco-build` to the Secret `build-<build id>-registry` in the builds namespace before it creates the Build, keyed by the host of the build's image repository, and deletes the Secret with the Build. It refuses a `StartBuild` without a credential. In `static` mode the agent writes none of these Secrets. The Application controller copies `loco-registry-pull-<workspace id>` into the workspace namespace as `loco-registry-pull` and attaches it to each workload ServiceAccount, and the build controller mounts `build-<build id>-registry` in the build's `fetch` and `push` steps; the [`loco-worker` chart README](https://github.com/team-loco/loco/blob/main/charts/loco-worker/README.md#registry-credentials) describes both modes.

The builder, which restores the build cache and pushes the image and cache, pings the registry before each of those steps. When the registry challenges with Bearer, the builder sends the `loco-build` credential from its docker config to the realm with HTTP Basic, asking for `pull` on its repository to restore the cache and `pull` and `push` to push. It fetches a new token once half of the token's `expires_in` has passed, measured from when it sent the request, so a push longer than the token lifetime never sends an expired token. On an HTTP 401 from the registry, which is how the registry answers an expired token or one signed with a key it no longer trusts, it fetches a new token and repeats the request. A token request that fails with a network error or HTTP 429 or 5xx is repeated; any other failure fails the build at once with an error naming the registry and the realm, including HTTP 401 or 403, which means the credential is no longer valid, for example because the build was cancelled. The repeated token request and the repeated registry request each stop after 5 attempts, waiting 1, 2, 4 and 8 seconds between them, and the build fails with an error naming the registry. The builder also uses go-containerregistry, so the realm must name the API by a DNS name for builds too. When the registry challenges with Basic, the builder sends the docker config credential to the registry directly.

`mise run e2e:registry-token` runs token mode end to end in a throwaway kind cluster. It starts the API with `LOCO_REGISTRY_AUTH=token`, then zot with `http.auth.bearer` pointed at the API's `/registry/token` and the key from `/.well-known/loco-registry-key.pem`, and installs `loco-worker` with `registry.auth: token`. The realm is a host name on the kind network, served by an nginx container that forwards to the API: go-containerregistry, which the builder and the image sweeper use, refuses a realm whose host is a private IP address unless it is the registry's own host. It deploys from source into two new workspaces and checks that no shared registry Secret exists, that the static `nodes`, `builder` and `api` passwords get 401, that each credential gets only its own workspace's or build's repository and the registry answers the rest with HTTP 401 and a Bearer challenge naming the refused repository, that a resent build gets a new credential and a finished build's credential gets 401, that renewal replaces a workspace's Secret and pods still pull, that removing a workspace's resource revokes its credential and the agent deletes its Secret, and that the image sweeper deletes a replaced image.

## Observability

OpenTelemetry collectors on each worker cluster export logs, traces and metrics over OTLP/HTTP to one configured endpoint, normally the control plane's observability proxy ingest role, which writes them to the control plane's ClickHouse. The proxy's query role serves the stored data.

Log message search is case sensitive and matches literal substrings. Percent signs, underscores and backslashes match themselves.

The observability proxy owns the ClickHouse schema. Before it serves, it applies the versioned migrations in `observability-proxy/migrations` to the `loco_obs` database, and `/readyz` fails until they succeed. Replicas take turns through a lock row in the `loco_migration_lock` KeeperMap table, stored in ClickHouse Keeper: each one claims the row while it migrates, renews its expiry every `MIGRATION_LOCK_RETRY_PERIOD` (2 seconds by default) until it finishes and deletes it after, so one migration runs at a time and a replica that finds the schema current applies nothing. A replica that dies holding the lock blocks the others until the row's `MIGRATION_LOCK_TTL` expiry (15 seconds by default) passes, and a holder that cannot renew stops migrating within that time. `MIGRATION_RETRY_BUDGET` (2 minutes by default) covers waiting for the lock and migrating together; a replica that runs out of it exits and restarts. The ingest role only inserts. Every table has `OrganizationId`, `WorkspaceId`, `EnvironmentId` and `ResourceId` columns, computed from the `loco.organization.id`, `loco.workspace.id`, `loco.environment.id` and `loco.resource.id` resource attributes, and its ordering key starts with `WorkspaceId`. The collectors set those attributes from the `loco.io/*-id` labels the controller puts on app and builder pods, and drop any value a client sends; Envoy's own telemetry takes `WorkspaceId` and `ResourceId` from the route instead and has no `OrganizationId` or `EnvironmentId`. Every collector also sets `loco.region` on every resource to the chart's `global.region`, replacing any value a client sends, so each row records the region of the cluster that collected it. `QueryMetrics` filters on `WorkspaceId` and the requested `ResourceId`s, and on `EnvironmentId` when the request sets `environment_id`, so a query that names an environment leaves out Envoy's metrics, and on `loco.region` when the request sets `region`. The dashboard's resource page names the active environment and region and sends queries through its configured control-plane API. That API forwards observability requests to its regional observability proxy. Rows expire after the proxy's `CLICKHOUSE_LOGS_TTL`, `CLICKHOUSE_TRACES_TTL` and `CLICKHOUSE_METRICS_TTL` durations, 365 days each by default; a migration applies them when it creates a table, so changing a duration later does not alter an existing table.

With `INGEST_ENABLED=true` the proxy also accepts OTLP logs, traces and metrics: OTLP/gRPC on `OTLP_GRPC_PORT` (4317) and OTLP/HTTP with protobuf bodies, optionally gzipped, on `OTLP_HTTP_PORT` (4318). OTLP/HTTP requests with any other content type, including JSON, return HTTP 415. It writes them with the OpenTelemetry Collector contrib ClickHouse exporter. Each request is written before it is answered. A storage failure returns HTTP 503 or gRPC `UNAVAILABLE`, which OTLP clients retry; an invalid request returns HTTP 400, HTTP 413 above `OTLP_MAX_REQUEST_BYTES`, or gRPC `INVALID_ARGUMENT`, which clients drop. Ingest keeps the tenancy attributes and `loco.region` that the worker collectors set, and sets `loco.cluster.id` from the ingest token as described below. `QUERY_ENABLED` (true by default) serves queries and runs the migrations. An ingest-only process has no migrator credentials: it waits up to `MIGRATION_RETRY_BUDGET` for the exporter's tables, starts the exporter so it detects their columns, and then reports ready.

Ingest requires an ingest token. Each enrolled agent calls `IngestService.IssueToken` with its cluster assertion and receives an Ed25519 JWT that the API signs with the OpenBao Transit key `LOCO_INGEST_TRANSIT_KEY`, which never leaves OpenBao, with `sub` set to the cluster ID, `aud` set to `loco-ingest`, a `jti`, and an expiry `LOCO_INGEST_TOKEN_LIFETIME` (1 hour by default) after `iat`. The agent requests a token at startup and again when half its remaining lifetime has passed, retries failures with its reconnect backoff, and writes the token to the Secret named by the `loco-worker` value `global.exporter.ingestToken.secretName` in both collector namespaces, where the collectors' `bearertokenauth` extension reads it. The proxy verifies the signature against the API's key set at `/.well-known/loco-ingest-jwks.json`, which holds every version of that key from its `min_decryption_version`, and refetches that set when a token names an unknown key ID, at most once per `INGEST_JWKS_REFRESH_INTERVAL` (30 seconds). A missing token, a bad signature or another audience returns HTTP 401 or gRPC `UNAUTHENTICATED`. An expired token, an unknown key ID within the refresh interval, or an unreachable API returns HTTP 503 with `Retry-After` set to `INGEST_RETRY_AFTER` (30 seconds), or gRPC `UNAVAILABLE` with `RetryInfo`, so collectors keep their queue until the agent renews the token.

The proxy fetches the workspaces placed on each sending cluster with `IngestService.ListPlacementWindows`, authenticated with that cluster's token, and caches them for `INGEST_PLACEMENT_CACHE_TTL` (30 seconds). The API opens a window when it places a resource on a cluster and closes it when it marks the placement for deletion, and keeps the window after the placement row is gone. A log record, span or metric data point whose resource names a `loco.workspace.id` is accepted only when that workspace had a window on the sending cluster at the record's time, widened by `INGEST_CLOCK_SKEW` (5 minutes) at both ends. A record without one, such as a Kubernetes event, platform telemetry or Envoy's own metrics, is accepted as a cluster-level row with an empty `WorkspaceId`. The proxy sets `loco.cluster.id` on every accepted resource to the cluster in the token, replacing any value the client sent, so every row names the cluster that sent it. Every query RPC requires a `workspace_id` and filters on `WorkspaceId`, so tenant queries never return cluster-level rows; operators read them from ClickHouse directly. Logs use their timestamp, or the observed timestamp when it is unset; spans use their start time; data points use their own timestamp. A record outside every cached window triggers one refetch per request, at most once per `INGEST_PLACEMENT_REFETCH_INTERVAL` (5 seconds). The proxy drops rejected records, writes the rest and reports the rejected count and reasons in the OTLP partial-success response. `loco_ingest_rejected_records_total` on the ingest role's `/metrics` counts them by `cluster` and `reason`: `workspace_not_placed` or `outside_placement_window`. For a removed cluster, the API refuses new tokens and `ListPlacementWindows` returns `PERMISSION_DENIED`; the proxy answers that cluster with HTTP 403 or gRPC `PERMISSION_DENIED` from its next fetch, at most `INGEST_PLACEMENT_CACHE_TTL` later.

`QueryLogs` and `TailLogs` accept an optional `environment_id`. A request that sets it reads only rows with that `EnvironmentId`, including every historical page and live-tail poll. Build logs have no runtime environment and are excluded by that filter. Omitting it retains workspace-wide queries, including build logs. Resource, severity, label and region filters apply together with the environment filter.

`QueryLogs`, `TailLogs`, `QueryMetrics`, `ListTraces` and `GetTrace` serve a caller with read on the workspace. A caller without it is served when the request names up to 100 resources in `resource_ids` and the caller has read on each one; a request that names none, or names one the caller cannot read, gets `PERMISSION_DENIED`. The query still filters on the requested workspace, so a named resource from another workspace returns no rows. Trace requests put `workspace_id`, `resource_ids` and `environment_id` in a shared `scope`. `ListTraces` returns one summary per trace with a total count, filters and paging; `GetTrace` returns all stored spans of one trace within that scope, without a time window or paging.

`QueryMetrics` reads scalar Gauge and Sum data, including counters such as `demo.payment.transactions`. Time filters apply to sample timestamps at nanosecond precision; returned point timestamps mark the start of each aggregation bucket. Each resource and time bucket aggregates the stored samples with `avg`, `sum`, `min`, `max`, `p50`, `p95` or `p99`, across the metric's attribute streams. Gauge results keep their existing shape. Sum series carry `metric_type: sum`, `aggregation_temporality` as the OTel enum number (`0` unspecified, `1` delta, `2` cumulative), and `is_monotonic: true` or `false`. Different sum temporalities and monotonicity flags produce separate series; a same-name gauge stays separate too. Clients must identify a series by its resource ID and labels.

These aggregations do not calculate rates or increases, convert delta and cumulative values, or compensate for counter resets. For cumulative samples `12`, `18`, `3`, `max` returns `18` and `sum` returns `33`, including the reset sample. Delta samples `2`, `4` produce a `sum` of `6`. Histograms, exponential histograms and summaries contain distributions and are outside this scalar endpoint. Queries retain workspace authorization and workspace, resource, environment, region, metric-name and time filters for both scalar tables.
