01 / Proposed direction

Replace deployment TOML with a small Go program that describes desired infrastructure. Keep the public workflow loco deploy, and add explicit loco infra plan and loco infra apply commands for review and automation.

The meaningful change is reconciliation. Evaluating Go is the front end. Loco also needs stable resource identity, ownership, live-state comparison, atomic desired-state updates, and plans that survive Git review without changing underneath it.
  • Go only: a separately versioned, typed SDK; ordinary compilation and execution in the customer’s local or CI environment.
  • One graph per named stack: multiple services in a repository share a definition. A workspace contains environments; each environment contains named stacks and their resource instances.
  • Server authority: the API validates and plans; PostgreSQL owns resource mappings and revisions. Customer repositories do not carry authoritative state files.
  • Clean break: delete the deployment TOML parser, types, writer, files and tests. There is no migration command, compatibility mode, deprecation period, fallback or future role for that file.
  • Confirmed environment model: staging and production run independent instances of the same service keys, with separate resource IDs, domains and secrets.
  • Confirmed merge behavior: a merge applies infrastructure and releases application code using the exact reviewed image digests.
  • Git optional locally: Git becomes mandatory for the reviewed-plan CI mode. A developer can initialize, plan, and deploy locally without creating a Git repository.
Planning premise: zero users. No customer configuration, deployed resource identity, database contents or public CLI/API contract needs a compatibility path. Design the target model directly; reset development data and regenerate examples as needed. Deletion of deployment TOML is the first implementation phase.

Proposed All new commands, SDK symbols, RPCs, tables, limits, and release gates below are design proposals. Repository findings are linked to the inspected commit. This document implements no platform changes.

02 / What Railway actually does

Railway’s current docs deprecate service-level JSON/TOML in favor of a project resource graph. TypeScript is generally available; Go and Python are beta. The CLI evaluates the program, computes a diff, and applies it. Railway does not evaluate the IaC program during an ordinary service deployment. Railway IaC documentation.

The Git integration saves a change set with an environment revision and the authoring tree. After merge, the action applies that artifact without re-evaluating the program; drift or a changed tree rejects the apply. Fork PRs are skipped. Railway Config Action.

Railway’s Go SDK provides authoring helpers for the graph, including context and named ownership slices. Loco should expose concrete Go structs and enums so common errors are compile errors. Railway Go SDK.

04 / Target model: environments own resource instances

Design the schema for the product we want

Use organization → workspace → environment → stack → resource instance. A stack is identified by (workspace_id, environment_id, stack_name); a service address is (stack_id, service_key). Every resource row has a required environment ID and belongs to exactly one stack. Display names are unique within an environment rather than globally across a workspace.

Staging and production can both contain service.api named api. Each environment has its own resource UUID, domains, region intent, secret namespace, deployments and placements. Evaluating the same Go module for another environment creates that environment’s graph; changing production never replaces staging’s workloads. There is no automatic environment suffix in the user-facing name.

Keep active-deployment uniqueness (resource_id, region) and placement uniqueness (resource_id, cluster_id) only because the resource UUID now identifies an environment-specific instance. Validate that any redundant deployment environment ID equals its resource’s environment ID. API queries, list filters, deletion and credential checks must join through that environment; workspace-global resource-name lookup is removed.

Agent Application names based on resource UUID can remain unique. Verify the controller’s namespace naming and deletion behavior against two distinct environment-specific resource IDs on the same cluster. Do not add duplicated environment keys to transport identities unless needed by that audit.

Environment-scoped authorization

Add environment as a TVM entity with hierarchy workspace → environment → resource. Plan credentials have environment read; apply credentials have environment write, with admin required for destructive operations. Target restrictions include the stack. Propagate the hierarchy through token issuance, scope expansion, interceptors, registry upload and the web access picker. Avoid preserving the old workspace-only permission model merely because it exists.

Supported graph

Multiple services, Dockerfile builds with explicit context, prebuilt image references, explicit region resources and autoscaling, routing, platform domains, health probes, variables, descriptions and observability. Every enabled region gets its own deployment snapshot. Regions have explicit CPU, memory and replica settings.

New Go definitions are the starting point. Choose defaults and validation for the Go contract directly; old TOML field names, version numbers, accepted ranges and omitted-value behavior do not constrain it. Existing operational limits such as cluster capacity still apply and must be enforced by the server.

The initial resource catalog supports services. Custom domains, database/cache/queue/blob provisioners, buildpacks and remote source builds require separate implementation; current placeholder protos do not make them functional. Go is the only authoring language in scope.

05 / Go authoring contract

Publish github.com/team-loco/loco/sdk/go as an independent Go module with semver tags sdk/go/vX.Y.Z. Keep its dependencies small; do not import the CLI’s internal config types, Docker, Connect clients, or the full root module. A pinned generated manifest package can live inside the SDK module and is generated from the canonical proto.

The customer owns an independent .loco/go.mod and .loco/go.sum. The application can be Node, Python, Rust, or anything else; only the infrastructure definition requires a Go toolchain. No app-level Go module changes are necessary.

package main

import loco "github.com/team-loco/loco/sdk/go"

func main() {
    loco.Run(func(ctx *loco.Context) *loco.Stack {
        replicas := int32(1)
        if ctx.EnvironmentType == "production" {
            replicas = 2
        }
        return &loco.Stack{
            Name: "storefront",
            Services: []*loco.Service{{
                Key: "api",
                Source: loco.Docker(".", "Dockerfile"),
                Hostname: "storefront-" + ctx.Environment + ".onloco.app",
                Spec: loco.Config(&loco.ServiceSpec{
                    Routing: &loco.Routing{Port: 8000},
                    Regions: map[string]*loco.Region{
                        "us-east-1": {
                            Enabled: true, Primary: true,
                            Cpu: "100m", Memory: "256Mi",
                            MinReplicas: replicas, MaxReplicas: replicas,
                        },
                    },
                    HealthCheck: &loco.Health{Path: "/health"},
                    Observability: &loco.Observability{
                        Logging: &loco.Logging{Enabled: loco.Value(false)},
                        Metrics: &loco.Metrics{Enabled: true},
                    },
                }),
                Variables: map[string]*loco.Variable{
                    "LOG_LEVEL": loco.Literal("info"),
                    "DATABASE_URL": loco.SecretRef("database-url"),
                },
            }},
        }
    })
}

loco.Run reads a versioned evaluation context from stdin and writes exactly one manifest to stdout. Context includes the resolved environment name, environment type, and project root; it never contains API tokens or secret values. Logs go to stderr. The envelope and stack identify the protocol version.

Use typed mutually exclusive source variants for Docker and image sources, and tagged variable variants for Literal, Preserve, and SecretRef. Use optional fields where zero differs from absent, especially logging enabled, tracing sample rate, health grace periods, and autoscaler targets. Application defaults are applied only by the API using its existing service defaults; SDK emission and offline validation preserve omission.

How loco.Context is supplied

The CLI resolves workspace and environment from flags, environment variables or a local link, then reads and validates their metadata through the API. It retains authoritative target IDs separately and supplies only sanitized authoring context to the compiled Go program through stdin: workspace name, environment name, environment type and project root. The SDK’s loco.Run decodes that JSON, invokes the callback and emits the resulting manifest on stdout.

Context comes from the selected deployment target, not from the user’s program. No API credentials or secret values are supplied. The API authorizes the CLI’s resolved target IDs when planning/applying, regardless of any target claims emitted by the program. For offline validation, explicit inputs can construct a context without an API lookup; real planning always resolves and verifies the live target.

Discovery and execution

  1. Find the nearest ancestor containing .loco/main.go, stopping at the Git root or filesystem root. The project root is its parent. --file explicitly selects a module entrypoint and --project-root overrides path anchoring.
  2. Compile the entire .loco package, not just one file. Helpers are allowed. Use go build -mod=readonly, GOWORK=off, and a pinned supported Go version. Readonly mode protects dependency files but can still download pinned modules.
  3. Execute the built binary with context cancellation, a proposed 30-second evaluation limit, and a proposed 5 MiB stdout limit. Compilation has a separate proposed 2-minute limit. Clean up process groups and temporary files.
  4. Decode one protobuf JSON envelope; reject unsupported versions, trailing output, unknown fields, duplicate keys, invalid names, and unsupported resource types.
  5. Resolve Dockerfile and env paths relative to project root and each declared context. Reject escapes and symlink escapes in CI; require the Dockerfile to be inside its build context.

Go execution is arbitrary customer code. Locally it runs with the developer’s OS permissions; environment filtering is not a sandbox. CI uses an isolated ephemeral runner, no credentials during compilation/evaluation, and a separate credentialed step that uploads the manifest to plan. Forks get compilation/validation only. Cloud execution of these programs requires an isolated worker design and is deferred.

Separate infrastructure review from application builds

infra apply does not implicitly run Docker. A new service with a Docker source can exist as infrastructure intent without a running release; the plan marks it as awaiting deployment. Configuration changes to running services create new runtime snapshots using their last pinned image. An image-source service can deploy its resolved digest directly.

deploy evaluates once, builds all selected images before committing desired infrastructure, freezes their digests, then asks the API for a combined deployment plan. A build failure leaves no half-created service graph. Registry blobs can remain unreferenced and be collected later. The existing tag generator does not assign DockerClient.ImageName; audit and fix this when extracting the build adapter.

07 / State, ownership and reconciliation

The canonical manifest lives in a new proto/loco/infra/v1/infra.proto. Its graph contains stable service keys, source recipes, resource defaults, region targets, domain intent, and tagged variable expressions. Normalize ordering and resource quantities before hashing; exclude local absolute paths, status, timestamps and generated IDs from desired-state equality.

Proposed storagePurpose / constraints
infra_stacksUUID, workspace UUID, environment UUID, stable name, dedicated revision, canonical desired manifest, protocol version. Unique (environment, name); enforce that environment belongs to workspace.
infra_resourcesStack UUID, logical key, resource UUID, desired hash and ownership metadata. Unique (stack, key), unique resource UUID. Every resource has a required environment and stack binding; renaming a display name preserves the instance UUID.
infra_plansServer-generated immutable operation payload, target, expected revisions, source digest, expiration and digest. API returns a redacted artifact referencing this payload; clients cannot edit approved operations.
infra_appliesPlan UUID, idempotency key, actor, source provenance, acceptance timestamp, affected deployment IDs, status. Unique (target, idempotency key). Acceptance and asynchronous readiness are separate.
resource_intent_revisionDedicated revision per resource. Every relevant direct API mutation must lock and increment it; health and agent observations do not.
infra_secret_versionsVersioned encrypted secret values and target-scoped references; redacted metadata visible to planner. Immutable version handles keep saved plans independent of later secret rotation.

Planner semantics

  • Create: unseen logical key. Check environment name uniqueness, platform domain availability and region/tier compatibility during planning and again at apply.
  • Update: replace managed settings on the same environment-owned resource UUID. Routing, probes, env, region resources and observability changes produce runtime snapshots where needed.
  • Rename: changing the display name preserves UUID. Changing a logical key is delete/create unless an explicit admin move operation changes the ownership mapping.
  • Prune: omitted owned keys produce deletes; resources owned by another stack are never pruned. New resources always have stack ownership; there is no transitional unowned population.
  • Region removal: stop that region’s active deployment, tombstone its placement, preserve historical deployment records. Do not delete a resource_regions row referenced by history; retain it with removing/retired intent.
  • No-op: unchanged normalized configuration and pinned runtime image do not create deployments or bump desired revisions. Runtime failure alone is not a configuration diff.
  • Drift: authorized direct mutations remain possible and increment revisions. The next plan shows the difference; old plans fail. Local edits become the next desired state only after a new review.

Start with the supported service graph; validate dependency references and cycles before adding richer resource kinds. Do not invent database endpoints or volume semantics while those provisioners are placeholders.

Server boundary

Add PlanInfrastructure, ApplyInfrastructure, GetStack, ListStacks. Planning performs no desired-infrastructure writes, image pushes, registry credential minting, or placement updates. Saving a plan records an immutable review artifact only. Apply calls shared internal transaction functions, not public RPC handlers and not a sequence of client-side CRUD requests.

New APIs use existing Connect interceptors, protobuf validation and TVM checks. Read access authorizes planning; write authorizes create/update/deploy; admin authorizes ownership moves and delete. Recheck all operation permissions at apply; possessing a plan file never authorizes execution.

08 / Exact plans and atomic apply

  1. Freeze inputs. Normalize the manifest; bind host, org/workspace/environment IDs, stack name, SDK/protocol/toolchain versions, source fingerprint, resource revisions, image digests and secret version handles.
  2. Review. The API returns a redacted operation list and an immutable plan ID/digest. Proposed expiry is 24 hours; expired or changed plans require another review. The saved file contains no token or plaintext secret.
  3. Preflight. Verify target, artifact integrity, expiry, source fingerprint and operation permissions. Resolve every required image, secret version, domain and cluster before writes. Reject unsupported schemas and missing references.
  4. Lock. In one PostgreSQL transaction, lock the workspace intent guard, stack, relevant resources and resource-region rows in a deterministic order. All competing CLI and dashboard mutation paths must participate.
  5. Compare and commit. Compare the frozen revisions to live revisions; reject drift with Connect Aborted. Apply resource specs, regions, domains, ownership, deployment snapshots and placement changes, record the idempotent apply, and bump intent revisions in the same transaction.
  6. Reconcile. Placement notifications are delivered on commit. The existing API → agent → Application → controller path runs asynchronously. --wait waits for all affected deployments, with timeout and failure exit codes.

A PostgreSQL transaction makes desired-state acceptance atomic; it cannot make several Kubernetes rollouts atomic. If one region fails after acceptance, retain the deployment IDs, show partial runtime readiness, and support a new reviewed rollback plan using earlier manifest/image/secret versions. Do not claim rollback undoes image uploads or recovers deleted data.

Retrying the same apply ID returns the recorded result even if the initial response was lost. A concurrent deploy, scale, domain edit, ownership change or env edit makes the plan stale. Cluster availability is checked live; a server-generated plan does not guarantee future capacity.

The current per-resource placement revision is a transport/reconciliation revision. It is not a replacement for a workspace/stack intent revision, and observed readiness updates must not continually invalidate reviewed plans.

09 / Variables, domains and the new service contract

Literal represents committed nonsecret configuration. SecretRef names a secret in the selected environment and freezes its immutable version during planning. Preserve can explicitly keep a live variable when editing a managed stack or using pull; it fails when no value exists. These are runtime semantics of the new system, not tools for reading old files.

Provide loco secret set and explicit secret import backed by encrypted, versioned, environment-scoped storage. Import is an ordinary secret-management operation independent of infrastructure authoring. Source files and generated Go never contain imported secret values. Pull emits secret references or Preserve expressions.

A saved plan references exact secret versions. If the version is unavailable at apply, fail; never silently resolve a newer value. Plain hashes of low-entropy secrets are not safe public diff markers; any equality fingerprint stays server-side and keyed. Secrets must not enter plan artifacts, PR comments, logs or user-facing errors. Reconcile the implementation with docs/tdd/secrets-handling.md, which is a proposed design rather than an existing versioned store.

Omitted keys delete variables previously owned by that stack. External variables are retained only under an explicit ownership policy; do not inherit accidental replacement behavior from the current env RPC. A stack’s field ownership rules apply equally to Go, dashboard and CLI mutations.

Platform hostname resolution matches an exact DNS label boundary and chooses the longest valid active suffix. An unmatched hostname errors instead of prompting for a different suffix. No domain means no public route. Domains belong to environment-specific resource instances, so staging and production must use distinct public hostnames.

10 / Git and GitHub Actions workflow

Commit the Go module, dependency lock, and definition. A trusted PR evaluates Go, builds changed application images and creates a combined infrastructure/deployment plan; reviewers read the redacted diff and pinned image digests; merge applies that saved payload and releases those images. Git is the review and provenance mechanism. Kubernetes still receives Loco’s API intent through the existing agent path.

  1. Evaluate without Loco credentials: compile and run the PR’s definition in a disposable job. Only same-repository trusted PRs proceed to credentialed planning. Fork PRs receive offline validation only; never use pull_request_target to execute their code with secrets.
  2. Build and publish: build changed Docker sources from the pinned PR tree on isolated runners without Loco apply credentials. Carry OCI artifacts to a separate trusted publisher using a stack/environment-scoped upload credential; resolve image-source declarations to digests. Reuse a previous digest only when its recorded source/build inputs are unchanged. Record source fingerprints, build recipes and image digests in images.json. Build and publish failures stop the workflow before desired-state mutation.
  3. Plan: upload the manifest and frozen image bindings in a separate step/job with a read-scoped target-bound token. Persist plan.json and a digest, then comment the redacted diff or use the job summary. Artifact identity includes repository ID, PR number, exact head SHA, target and successful workflow run ID.
  4. Merge: check out the merge result and download only the artifact from that PR head’s successful trusted plan run. Validate provenance, checksum, target, expiration and source inputs; never select “latest artifact” by name.
  5. Apply: use a separate write/admin credential limited to that stack’s target. Invoke loco infra apply --plan plan.json --yes; destructive operations also need explicit workflow policy approval. This applies resource configuration and schedules releases from the saved image bindings. No Go program is evaluated and no application image is rebuilt in this stage.
  6. Reject stale review: if state or inputs changed, stop and generate a replacement plan requiring review. Serialization/concurrency helps but does not replace API compare-and-swap.

Source pinning must cover more than one file

For infrastructure-only plans, fingerprint the entire .loco/ module, module files, pinned SDK and local dependencies; v1 rejects external local replace directives and untracked inputs in reviewed CI. Ignore only declared runtime output paths such as plan.json, link metadata and cache. Hashing just main.go is insufficient.

For a deployment plan, also freeze each application build context, Dockerfile, ignore rules and final image digest. The simple v1 CI rule is to fingerprint the full tracked repository tree, excluding only declared artifacts/local state, and reject submodules or unresolved LFS content until supported. Changes outside .loco/ must trigger planning when they affect a reviewed deployment. A merge commit SHA can differ from a PR SHA while its relevant source tree is identical.

Local deployment can use a dirty working directory with a content fingerprint. Saved reviewed CI plans require tracked, clean inputs. Keep local provenance distinct from a Git-reviewed artifact. Do not re-execute arbitrary Go merely to verify a saved plan.

Application image delivery

The default action includes application delivery from its first release. Build and push changed images before generating the reviewed plan and record their exact digests. A source-only application change must produce a deployment operation even when the Go definition is unchanged. For new resources, use stack-scoped staging image tags rather than tags requiring a resource UUID that does not exist yet. Add a target-authorized registry upload endpoint; do not reuse the current user-read check as authorization for a workspace-wide CI upload.

loco infra apply remains available for deliberate configuration-only operations. The default merge workflow applies the combined saved plan, rather than following it with a fresh deployment plan. Source fetching, builds and uploads run in GitHub Actions initially; a Loco-hosted build service and GitHub App are separate implementation options.

12 / Delete the old authoring path

Deployment TOML is removed, not deprecated. There are no users to migrate and no customer definitions or resource UUIDs to preserve. No migration command, reader, compatibility alias, detection path, translation layer, staged cutoff or filename repurposing belongs in this design.

  1. Delete the implementation. Remove the deployment-config loader, writer, TOML-specific types and default generator. Remove the old path resolver and --config flag. Decouple the Docker builder from deleted config types.
  2. Delete the files. Remove root and example deployment TOML files, its field reference, and TOML command fixtures. Remove its deployment documentation and roadmap entries.
  3. Rebuild examples. Write fresh Go modules for examples/test-api/ and examples/metrics-validation/, based on the new service contract. Test the monorepo build contexts and observability behavior directly.
  4. Reshape schemas and callers together. Make resource instances environment-owned, change protobuf contracts and APIs, regenerate code, rebuild CLI/web callers and reset development seed data where needed.
  5. Release one coherent system. Publish the Go SDK, CLI and action together after the new deploy and reviewed-plan workflow work end to end. No transitional authoring system is shipped.

A missing Go definition produces the ordinary loco init guidance. An unsupported --file input fails as unsupported input. The new loader never checks for deployment TOML or attaches special behavior to that filename.

User CLI settings are a separate subsystem. Its existing ~/.loco/config.toml can remain if useful; that does not preserve any deployment TOML path. Remove the TOML library only if no remaining independent settings code requires it.
